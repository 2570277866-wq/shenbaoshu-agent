# 节点 · 一致性审查（LLM 语义部分）

> **分工：** 数字类检查（1/2/3/4/6 项）走代码节点 ③，确定性判定。
> 本文档只负责**语义类检查**（第 5、7 项）—— 代码判不了，必须 LLM 读。
> 两者结果合并为 `chk_report`。

## 输入组装

| 变量 | 来源 | 说明 |
|---|---|---|
| `gen_document` | 代码节点 ② | 完整 Markdown 成稿 |
| `kb_style` | 风格库 | **用于比对是否串入事实** |
| `gen_elements` | 节点 ① | 判定数字一致性的基准 |
| `chk_code_report` | 代码节点 ③ | 已完成确定性检查的结果 |

**装配方式：** 代码节点 ③ 先跑确定性检查，把 `gen_document` 与 `kb_style` 一并组装进本节点的 prompt。**先代码后 LLM**，因为数字问题一旦发现可短路回退，不必浪费一次 LLM 调用。

## 任务

审查以下两项，输出问题清单。

### 检查项 5：空缺统计

扫描全文 `【待补充：xxx】`，统计数量与分布章节。

**判定：** 数量 > 0 不阻断流程，但必须计入报告，提示人工补全。
**异常：** 单章节标注密度过高（> 3 处），说明该章节素材严重不足，标记该章节为"素材缺口"。

### 检查项 7：风格未串事实 ★

比对 `gen_document` 与 `kb_style`，检测是否混入了**风格库范文的事实内容**。

**高发形态：**

- 范文中的企业名称、产品名称出现在成稿中
- 范文中的具体数据（营收、人数、年限）被搬入
- 范文中的专利号、证书号被搬入
- 范文中的项目案例、客户名称被搬入

**判定：** 命中任一即 `pass: false`，标记为**严重问题** —— 这是把别家公司的信息写进了本企业的申报书。

**注意：** 语体、句式、论证结构与范文相似是**正常的**，不报。只报事实性内容的搬运。

## 输出

```json
{
  "pass": false,
  "issues": [
    {
      "type": "style_fact_leak",
      "severity": "critical",
      "section": "项目背景",
      "detail": "出现'××科技有限公司'，该名称来自风格库范文，素材库中无此企业",
      "evidence": "原文片段"
    },
    {
      "type": "missing_data_density",
      "severity": "medium",
      "section": "经费预算",
      "detail": "该章节有 5 处【待补充】，素材缺口明显",
      "evidence": ""
    }
  ]
}
```

## 硬约束

1. **只报问题，不改稿。** 本节点不产出修改后的文本。
2. **每条问题必须带 `evidence`**（原文片段），否则无法定位。
3. **不报语体、格式、字数问题** —— 那些由代码节点负责。
4. **不确定的不报。** 疑似但无法确认是范文事实的，降级为 `severity: "low"` 并说明不确定原因，不阻断流程。
