# 节点 · 要素抽取

> 对应代码执行节点 ①。**规则优先，LLM 兜底。**
> 数字抽取走正则与规则，LLM 只处理纯文本段落中的定性信息。

## 输入

| 变量 | 来源 | 说明 |
|---|---|---|
| `kb_material_tech` | 知识库 · 素材-企业技术参数 | 检索 top-k |
| `kb_material_ip` | 知识库 · 素材-知识产权 | |
| `kb_material_finance` | 知识库 · 素材-财务数据 | |
| `in_team_size` | 用户输入 | 作为交叉校验基准 |
| `in_budget_range` | 用户输入 | 同上 |

## 任务

把散落的素材条目抽成一份**全局要素表**，作为后续全部章节的硬约束。

## 输出

```json
{
  "project_name": "",
  "team_size": 0,
  "duration_months": 0,
  "total_budget": 0,
  "budget_breakdown": {},
  "core_metrics": [
    {"name": "", "target": "", "baseline": "", "source": ""}
  ],
  "ip_list": [
    {"type": "", "count": 0, "status": "", "numbers": [], "source": ""}
  ],
  "qualifications": [
    {"name": "", "issuer": "", "date": "", "source": ""}
  ],
  "missing": []
}
```

## 硬约束

1. **不推算。** 抽不到的字段进 `missing` 数组，不填默认值、不填估值、不填行业均值。
2. **不改写数字。** 原样保留，不四舍五入，不做单位换算。
3. **每个数值带 `source`**，指回素材条目原文 —— 这是节点 ③ 回溯校验的唯一依据。无 `source` 的数值视为无效。
4. **冲突时以用户输入为准**（`in_team_size` vs 素材中的团队规模），并把冲突记入 `missing` 供人工确认。
5. `missing` 中每一项写清缺什么，例如 `"2024年度研发投入金额及占营收比例"`，不写"财务数据不全"这种笼统描述。

## 抽取方法

| 字段 | 方法 |
|---|---|
| 金额、人数、数量、周期 | 正则 + 单位识别，LLM 不参与 |
| 专利号、证书号 | 正则匹配编号格式（如 `ZL\d{9,}`、`软著字第\d+号`） |
| 指标名 / 目标值 / 基线值 | 表格解析优先，无表格时 LLM 抽取 + 原文校验 |
| 资质名称、颁发机构、日期 | LLM 抽取，必须回填原文片段作为 `source` |
| 定性描述 | LLM 抽取，标记 `"type": "qualitative"`，不作为数字依据 |

## 自检

- [ ] `missing` 里的字段是否真的在素材中不存在？（不是没找到而是没抽到）
- [ ] 每个数值都有 `source`？
- [ ] 有没有出现素材中不存在的数字？
- [ ] 用户输入与素材冲突的地方是否已记录？
