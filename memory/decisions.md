## 2026-09-18 — 记忆服务用 FastAPI，不用标准库 http.server

**决策：** 5 个记忆工具实现为 `memory_service/`（FastAPI + uvicorn），HTTP 端点供 Dify
HTTP 节点调用。不采用标准库 `http.server` 自建。

**理由：** 否掉了 http.server —— 它能少一个依赖，但这个服务要写 Agent 的记忆文件，
而记忆文件会**注入 system prompt**，是攻击面。手写 `http.server` 意味着请求体校验、
错误响应形状、路由全部自己维护，出错方式是「静默接受了一个畸形请求」。
FastAPI 这几件事都是框架保证的：pydantic 校验请求体、异常处理器统一错误出口
（`{"ok": false, "error": {"code", ...}}`，Dify 分支要读 `code`）、`/docs` 可点着调试
（对接 B 与交付培训时省事）。省下的那点依赖成本，换的是不需要自己写校验代码。

**不影响既定约束：** 「仅标准库」那条是给 **Dify 代码执行节点**的（沙箱只保证标准库）。
记忆服务是独立进程，不受限。

**代价/影响：**

- 多一个 venv 和一份依赖要锁（`requirements.txt`）；目标机要能装 Python 包
- 与 Dify 同机部署，**Docker 网络连通性有坑**：容器内的 `127.0.0.1` 是容器自己。
  Mac/Win 用 `host.docker.internal`，Linux bridge 网络要绑 `172.17.0.1`。
  见 `memory_service/README.md`
- 绑非本机地址时强制要求令牌 —— 代码里的硬校验，不是文档约定

**推翻条件：** 目标机装不了 venv，或交付要求零第三方依赖 → 退回 `http.server`。
届时 `store.py` 不用动，只换 HTTP 层。

**验证状态：** ✅ 51 项单测全绿；真实 HTTP 冒烟通过（read / list / inject / 路径穿越拦截 /
insert 预演），真记忆文件 sha 未变。

## 2026-09-18 — 「数字可回溯」定为 warn 级，不阻断

**决策：** 一致性审查第 2 项（正文数字能否回溯到素材）判定为 `warn`，不计入 `pass`。其余
六项中，数字矛盾、杜撰资质、占位符残留、风格串事实为 `block`；空缺统计与章节字数为 `warn`。

**理由：** 正文里出现一个素材中查不到的数字，可能是**合理派生** —— 占比、合计、年份、
文号。把第 2 项做成阻断，回退循环会停不下来：重试 2 次仍不过 → 整篇作废，而人看一眼就能
判断这个数字该不该在。**阻断的代价（丢掉整篇）大于漏放的代价（人工审核时发现）。**

反过来，杜撰专利号必须阻断 —— 那是「看似合理但错误」的典型，人看不出来，且是 R1 风险
（幻觉）的直接出口。

**影响：**
- `check_consistency.py` 的 `BLOCKING_TYPES` 是唯一开关
- 条件分支节点只读 `pass`，不自己判 severity
- 第 2 项的噪声由人工审核清单兜底（`docs/使用指南.md`）

**推翻条件：** 若实测发现第 2 项的误报率很低（< 5%），可考虑升为 block；若误报率高到
淹没真问题，可考虑关掉该项、只留杜撰资质检查。

**验证状态：** ⬜ 待做。需真实项目跑完 3 份后统计第 2 项的误报率。

## 2026-09-18 — Embedding 选 qwen3-embedding:0.6b-fp16

**决策：** Embedding 模型用 `qwen3-embedding:0.6b-fp16`（阿里 Qwen3-Embedding-0.6B，Ollama 部署，fp16 全精度）。生成模型同选 Qwen3 系列。

**理由：**

1. **按弱的一方定。** 目标机显存 1GB，embedding 只能跑 CPU，因此必须选 CPU 跑得动的规格。4B fp16 要 8GB、8B fp16 要 15GB，CPU 上不可用。
2. **fp16 不量化。** 0.6B 全精度才 1.2GB，省这点体积无意义。而 embedding 的量化损失比生成模型更伤 —— 生成模型量化是措辞变差，embedding 量化是向量空间偏移，直接伤检索。
3. **32K 上下文**（vs bge-m3 的 8K）。素材条目可整条入库，长文档不用切碎。
4. **Apache 2.0**，商用无顾虑。
5. **Ollama 一条命令安装**，A 与 B 用同一命令，一致性最容易保证。

**代价与风险：**

- **必须锁 digest，不能用 tag。** tag 浮动，上游更新即变；A/B 不同 digest = 两个模型，检索失准且不报错。
- **⚠️ 别用 `latest`** —— 它指向 `8b-q4_K_M`，是另一个东西，且 CPU 跑不动。必须显式 `ollama pull qwen3-embedding:0.6b-fp16`。
- **Qwen3-Embedding 是指令感知模型。** 若一方加 `Instruct:...Query:` 前缀、另一方不加，向量不在同一空间 —— 同样检索失准且不报错。约定两边都不用前缀，且都用 Ollama（不一边 Ollama 一边 transformers）。

**纠正：** 早期把 bge-m3 的"原生稀疏向量"当作混合检索的必要条件，**这是错的**。Dify 的混合检索是向量 + 全文检索，由向量库实现，不需要模型输出稀疏向量，稠密向量模型完全够用。

**推翻条件：** 召回验证 < 90% 且排查后确认是模型能力问题（而非知识库建设问题）时，换 `qwen3-embedding:4b-q4_K_M`。

**验证状态：** ⬜ 待做。需完成 `ollama pull` → 记 digest → 20–30 题测试集 → 召回率 ≥ 90%。

## 2026-09-18 — 推理层外置（目标机显存 1GB 逼出来的）

**决策：** 推理层与编排层解耦。目标运行机（显存 1GB）只跑 Dify + 向量库 + 记忆服务 + XXL-JOB，全部 CPU；模型推理走网络调外置的 Ollama/vLLM 服务。

**理由：** 目标机 1GB 显存跑不了任何本地模型（7B Q4 需 ~6GB），连 embedding 都放不下。而 Ollama 本身是网络服务，`OLLAMA_HOST=0.0.0.0` 暴露即可，Dify 模型接入填 URL，**代码零改动**。这不是设计选择，是硬件约束。

**影响：**

- 把原定"阶段三：推理服务与 Dify 分离"提前到阶段一
- Embedding 也走 CPU（bge 系列 CPU 索引可接受，单次查询 ~100ms）
- 推理机候选按合规性排序：局域网 GPU 服务器 > 云 GPU 实例 > 云 API（排除）
- **若推理机上云，"数据不出内网"承诺需改为"数据不出专属实例"，须与企业书面确认**

**推翻条件：** 拿到有 GPU 的目标运行机（≥12GB 显存）时可回归单机形态。

## 2026-09-17 — memory/ 是运行时 Agent 的记忆，由 Agent 写入

**决策：** `memory/` 目录是**运行时申报书 Agent** 的记忆，由该 Agent 通过 5 个记忆工具（`memory_read` / `write` / `replace` / `insert` / `list`）读写。**Claude Code 是开发工具，不写 `memory/`。**

**理由：** 两者职责不同 —— Claude Code 负责开发、调试、写文档；申报书 Agent 负责运行时生成与记忆沉淀。混淆会导致记忆内容混杂开发笔记与运行经验，失去可用性。

**影响：**

- 开发进度与待办 → 记 `CLAUDE.md`「当前任务」，不记 `memory/CONTEXT.md`
- `CONTEXT.md` 与 `AGENTS.md` 是运行时 Agent 的身份与规则，启动时注入其 system prompt
- `decisions.md` / `lessons.md` 由运行时 Agent 在生成后与人工修改后写入
- Claude Code 可以**设计、调试、验证**记忆系统，但不代写记忆内容

**实现缺口：** Dify 的 LLM 节点访问不到本地文件系统，代码节点沙箱也不保证可持久读写。5 个工具需落地为**本地记忆服务**（HTTP 接口），由 Dify HTTP 节点调用。设计见 `docs/ARCHITECTURE.md` 第九节。

## 2026-09-17 — 编排层选 Dify，不用 LangChain

**决策：** 工作流编排用 Dify（本地 Docker 部署），LangChain/LangGraph 作为备选但不采用。

**理由：** ① 交付对象是企业非技术人员，需要可视化界面；② RAG 是核心需求，Dify 内置，自建 RAG 不是本项目创新点；③ 立项汇报需要流程图，可视化本身是说服力；④ 阶段一 20–30 天出结果，改流程的成本远低于改代码；⑤ 团队工程能力有限，维护 LangChain 服务是持续负担。

**接受的代价：** 复杂逻辑受平台限制（用代码执行节点承载）；工作流难做单元测试（关键校验抽到 `scripts/` 独立脚本）；版本升级可能破坏工作流（锁版本 + 导出入库）。

**推翻条件：** 需要复杂多轮 Agent 循环 / 多租户隔离超出 Dify 能力 / 节点数无法维护 / 需要灰度发布。届时只换编排层，提示词、脚本、知识库素材均已独立存放。

## 2026-09-17 — 要素表作为全局一致性约束

**决策：** 在逐章节生成之前，先用代码执行节点抽取一份全局要素表（人员/预算/周期/核心指标），所有章节生成时统一注入。

**理由：** 长文档分块生成最大的坑是章节间自相矛盾（背景写 8 人、团队写 12 人）。让各章节共享同一份要素表，从结构上消除分歧，比事后审查更可靠。

**影响：** 工作流增加节点 4；提示词中需明确"要素表为硬约束，不得自行编造"。

## 2026-09-17 — 三类知识库分库，不混放

**决策：** 知识库按类型分三类 —— 模板（结构）、素材（事实）、风格（表达），分库存储、分别检索。

**理由：** 三类知识的分块策略、更新频率、检索用途完全不同。混在一个库里会导致"问技术方案怎么写，召回企业财务数据"这类失准。

**影响：** 6 个知识库（CLAUDE.md 4.3）；检索节点分渠道召回；模板类按章节切、素材类按条目切、风格类按段落切。
