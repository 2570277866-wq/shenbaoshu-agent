## 一、硬件与算力规划

### 1.0 现状（2026-09-18）

| 机器 | 配置 | 用途 | 能跑什么 |
|---|---|---|---|
| **开发机** | Mac + 独显机 | 开发、调试、验证 | Mac 走 Metal，独显走 CUDA，开发阶段够用 |
| **目标运行机** | **显存 1GB** | 交付后自动执行 | ❌ **跑不了任何本地模型**（7B Q4 需 ~6GB） |

**结论：推理层必须外置。** 目标机只做编排（Dify + 向量库 + 记忆服务 + XXL-JOB），全部 CPU 可胜任。

部署拓扑见 `docs/ARCHITECTURE.md` 1.1。

**待确认：** 局域网内是否有可用的 GPU 服务器（实验室 / 公司 / 合作单位）。有则合规问题消失、成本为零，是当前最优先要问的一件事。没有才考虑云 GPU 实例。

### 1.1 模型规模 → 显存需求（Q4_K_M 量化，含 8K 上下文 KV cache）

| 模型规模 | 权重显存 | +KV cache | 建议最低显存 | 4090 上大致速度 |
|---|---|---|---|---|
| 7B | ~4.5 GB | ~1 GB | 8 GB | 60–100 tok/s |
| 14B | ~9 GB | ~1.5 GB | 16 GB | 30–50 tok/s |
| 32B | ~20 GB | ~2.5 GB | 32 GB（24 GB 需限上下文） | 15–25 tok/s |
| 70B | ~40 GB | ~4 GB | 48 GB+ | 单卡跑不动 |

> 数字为量级估算，**必须实测确认**。申报书单章节约 1500–3000 字，按 20 tok/s 计，单章节 2–5 分钟，全篇 7 章节串行约 20–40 分钟 —— 体感可接受，但必须实测。

### 1.2 三阶段硬件规划

> 以下为**推理机**的采购/租用评估。目标运行机不在评估范围内 —— 它不需要 GPU。

#### 当前（试水）：单机消费级

| 项 | 配置 | 说明 |
|---|---|---|
| GPU | RTX 4090 24GB（或 3090 24GB） | 24GB 是能跑 32B 量化的门槛 |
| 内存 | 64 GB | 模型加载 + Dify + 向量库 |
| 存储 | 1 TB NVMe | 模型文件大（32B Q4 ≈ 20GB/个） |
| 系统 | Linux（推荐）或 Windows + WSL2 | Docker 部署 |

**能跑：** 7B / 14B 流畅，32B 可用但需限制上下文。
**瓶颈：** 单用户、串行生成、无并发。

#### 近期升级：单机专业卡

| 项 | 配置 | 收益 |
|---|---|---|
| GPU | RTX 6000 Ada 48GB / A6000 48GB / L40S 48GB | 70B Q4 可跑；32B 可开长上下文 + 并发 |
| 内存 | 128 GB | |
| 推理框架 | Ollama → vLLM | 并发吞吐提升显著，Ollama 串行是瓶颈 |

**触发条件：** 阶段二有 ≥ 3 家企业同时使用，或需要 70B 提升质量。

#### 中期扩展：多卡 / 多机

| 项 | 配置 | 说明 |
|---|---|---|
| GPU | 2× 48GB 或 4× 24GB | 张量并行，跑更大模型 |
| 推理 | vLLM / TensorRT-LLM | 批处理、并发、量化优化 |
| 部署 | 推理服务与 Dify 分离 | 独立扩缩容 |

**触发条件：** 阶段三平台化，多租户并发。

### 1.3 决策要点

1. **先试水再投入。** 阶段一用现有机器验证可行性与生成质量，达标才谈升级。
2. **显存优先于算力。** 跑得动 > 跑得快。24GB 换 48GB 的价值远大于换更强的 24GB 卡。
3. **推理框架跟进。** 单用户 Ollama 够用；一旦有并发，vLLM 是必须的，不是优化。
4. **量化档位。** Q4_K_M 是质量/显存平衡点。申报书是正式文书，不建议低于 Q4。
5. **统一内存方案（备选）。** Mac Studio 大内存版可跑大模型，但速度低于同价位 GPU 方案。仅在没有 NVIDIA 卡时考虑。

### 1.4 算力预算参考

| 方案 | 大致成本 | 能跑 | 适合阶段 |
|---|---|---|---|
| 现有机器 + 4090 | 已有 / 1.5–2 万 | 14B 流畅 | 阶段一 |
| 单张 48GB 专业卡 | 4–6 万 | 32B 流畅、70B 勉强 | 阶段二 |
| 双卡 48GB 工作站 | 10 万+ | 70B 流畅、可并发 | 阶段三 |

> 价格为量级参考，需按实际采购询价。

### 1.5 云 GPU 实例（备选方案）

**前提：** 局域网内无可用的 GPU 服务器。

| 类型 | 大致成本 | 说明 |
|---|---|---|
| 按小时租消费级卡（AutoDL / 共绩 / 恒源云等） | ¥2–3/小时（4090） | 只在开发/生成时开机，最省 |
| 云厂商 GPU 实例按量（A10 24GB 级） | ¥10–20/小时 | 更稳，网络与合规支持更好 |
| 包月云 GPU | ¥2000–4000/月 | 开发期连续使用 |

**成本测算：** 按每天 8 小时、25 个工作日计，按小时租约 ¥400–600；包月约 ¥2000–4000。**20–30 个工作日的项目，租比买划算。**

**部署方式与本地完全一致**（Docker + Ollama），代码零改动，只改 `OLLAMA_HOST` 与 Dify 的模型接入 URL。

**⚠️ 合规影响：**

| | 本地/局域网 | 云 GPU 实例 | 云 API |
|---|---|---|---|
| 数据流向 | 不出内网 | 进你的专属云主机 | 进第三方推理服务与日志 |
| 承诺表述 | "数据不出内网" | "数据不出专属实例" | 无法承诺 |
| 需否重新与企业沟通 | 否 | **是** | **是，且需企业明确同意** |

**租实例 ≠ 调 API。** 前者是换机房，后者是交出数据。**云 API 方案建议直接排除** —— 申报书素材含企业技术秘密。

**上云前必须做的：**
1. 与企业重新确认数据边界，书面确认
2. 云实例磁盘加密、快照策略确认
3. 实例只开必要端口，推理服务加访问控制（不裸奔在公网）
4. 用后销毁实例时确认数据清除

## 二、技术选型对比：Dify vs LangChain

### 2.1 对比

| 维度 | Dify | LangChain / LangGraph |
|---|---|---|
| **形态** | 可视化编排平台（Web UI） | 代码框架（Python/JS 库） |
| **上手** | 拖拽即可，非技术人员可看懂 | 需 Python 工程能力 |
| **RAG 支持** | 内置，含知识库管理、分块、检索、重排 | 需自行搭建，组件自选 |
| **流程控制** | 条件分支、迭代、循环（UI 配置） | 全代码，任意复杂逻辑 |
| **调试** | 节点级运行日志、单步测试 | 依赖自建日志或 LangSmith |
| **版本管理** | 导出 YAML，但非文本 diff 友好 | Git 原生，diff/PR 完整 |
| **可测试性** | 弱，无单测概念 | 强，可写单元测试与 CI |
| **定制上限** | 受平台限制，复杂逻辑需代码节点绕 | 无上限 |
| **多租户/权限** | 有基础支持 | 需自建 |
| **部署** | Docker Compose 一键 | 自建服务 |
| **生态** | 插件市场、模型接入丰富 | 生态最大，集成最多 |
| **稳定性** | 版本升级可能破坏已有工作流 | API 变动较频繁，锁定版本可解 |
| **学习曲线** | 低 | 高 |

### 2.2 结论：选 Dify

**理由（按权重）：**

1. **交付对象是非技术人员。** 企业操作员需要看懂的界面，LangChain 做不到。
2. **RAG 是核心，Dify 内置。** 自建 RAG 要处理分块策略、向量库、rerank，工作量不小，且不是本项目创新点。
3. **演示与汇报需要可视化。** 立项汇报时流程图本身就是说服力。
4. **迭代速度优先。** 阶段一要在 20–30 天内出结果，Dify 的调试与改流程成本远低于改代码。
5. **团队工程能力有限。** 维护一套 LangChain 服务是持续负担。

**代价（明确接受）：**

| 代价 | 缓解 |
|---|---|
| 复杂逻辑受平台限制 | 用代码执行节点承载，脚本放 `scripts/`，逻辑仍可测 |
| 工作流难以做单元测试 | 关键校验逻辑抽到 Python 脚本，脚本可独立测试 |
| 版本升级风险 | 锁定版本 + 导出配置文件入库 + 升级前回归测试 |
| 长期可能触到天花板 | 阶段三若受限，把推理服务与 RAG 层拆出来，Dify 仅作编排 |

### 2.3 什么时候该换掉 Dify

不是"以后一定要换"，而是触到以下任一条时重新评估：

- 需要复杂的多轮 Agent 决策循环，UI 编排绕不出来
- 多租户隔离要求超出 Dify 能力
- 工作流节点数增长到无法维护
- 需要 A/B 测试与灰度发布

**架构预留：** 提示词、校验脚本、知识库素材均已独立于 Dify 存放（`dify/prompts/`、`scripts/`、`knowledge/`），迁移时保留资产，只换编排层。

## 三、推理框架：Ollama vs vLLM

| | Ollama | vLLM |
|---|---|---|
| 定位 | 本地单用户，开箱即用 | 生产级推理服务 |
| 并发 | 差（串行） | 强（连续批处理） |
| 显存利用 | 一般 | 优（PagedAttention） |
| 部署复杂度 | 低 | 中 |
| 适用阶段 | 阶段一 | 阶段二起 |

**切换时机：** 出现并发需求，或单份生成耗时因排队而劣化。不是性能优化，是架构要求。

## 四、Embedding 模型选型与确认

> ⚠️ **这是全项目最急的一环。** 型号未定 → 知识库无法建索引 → 第 1 周全线卡死。
> **A 先定，再通知 B 对齐** —— 不商量，只通知。

### 4.1 选型标准

| # | 标准 | 理由 |
|---|---|---|
| 1 | 许可协议允许商用 | 申报书是商业用途，非商用权重是法律雷 |
| 2 | A 与 B 两边都能装 | 一致性是硬约束，装法越简单越不容易出错 |
| 3 | 上下文 ≥ 512，越长越好 | 素材条目不能切太碎 |
| 4 | 支持稀疏向量 | 架构定的是混合检索 |
| 5 | CPU 可跑 | 目标机显存 1GB，GPU 指望不上 |
| 6 | 中文效果 | |

### 4.2 选定：`qwen3-embedding:0.6b-fp16`

| 项 | 值 |
|---|---|
| 模型 | Qwen3-Embedding-0.6B（阿里） |
| 许可 | **Apache 2.0** ✅ 商用无忧 |
| 维度 | 1024（支持 MRL 截断） |
| 上下文 | **32K** |
| 量化 | **fp16 全精度，不量化** |
| 大小 | 1.2GB |
| 部署 | Ollama：`ollama pull qwen3-embedding:0.6b-fp16` |
| CPU 推理 | 可跑，速度可接受 |

**为什么选 0.6B 而不是 4B / 8B：**

**按弱的一方定。** 目标机显存 1GB，embedding 只能跑 CPU —— 那就必须选 CPU 跑得动的规格。4B fp16 要 8GB、8B fp16 要 15GB，CPU 上慢到不可用。

**为什么用 fp16 而不是 q4：**

0.6B 全精度才 1.2GB，省这点体积没意义。而 **embedding 模型的量化损失比生成模型更伤向量质量** —— 生成模型量化后是措辞变差，embedding 量化后是向量空间偏移，直接伤检索。

**选它的理由：**

1. **Ollama 一条命令安装** —— 两边同一条命令，一致性最容易保证（最关键）
2. **32K 上下文** —— 素材条目整条入库，长文档不用切碎
3. **Apache 2.0** —— 商用无顾虑
4. **中文强** —— MTEB 多语言榜靠前

**备选（仅当验证不通过时启用）：**

| 模型 | 许可 | 短板 |
|---|---|---|
| `bge-m3` | MIT | 上下文仅 8K |
| `qwen3-embedding:4b-q4_K_M` | Apache 2.0 | 2.5GB，CPU 偏慢 |

> **纠正一处早期判断：** 曾把 bge-m3 的"原生稀疏向量"当成混合检索的必要条件 —— **这是错的**。Dify 的「混合检索」是向量 + 全文检索，由向量库实现，不需要模型输出稀疏向量。**稠密向量模型完全够用。**

### 4.3 确认步骤

```bash
# 1. 装（显式指定规格，不用 latest —— latest 指向 8b-q4_K_M）
ollama pull qwen3-embedding:0.6b-fp16

# 2. 查看模型信息
ollama show qwen3-embedding:0.6b-fp16

# 3. ★ 记录 digest
ollama list
```

**★ 锁 digest，不是锁 tag。**

tag 是浮动的，上游更新后 digest 会变。A 和 B 若拉到不同 digest，就是两个模型 —— **检索失准且不报错**，症状隐蔽，排查极耗时。

**⚠️ 注意 `latest` 指向 `8b-q4_K_M`。** 决不能用 `ollama pull qwen3-embedding` —— 那会拉到 8B 量化版，跟你选的完全是两个东西，且 CPU 跑不动。

### 4.4 与 B 对齐的字段

```
模型：qwen3-embedding:0.6b-fp16
来源：Ollama registry
digest：sha256:xxxxxxxx（从 ollama list 抄）
维度：1024
上下文：32768
量化：fp16（全精度，未量化）
部署方式：Ollama，版本号 ____（两边一致）
指令前缀：不使用（两边一致）★
```

**★ 指令前缀这条容易漏。**

Qwen3-Embedding 是**指令感知**模型，支持给查询加 `Instruct: ... Query: ...` 前缀。

**若 A 加了前缀、B 没加，向量就不在同一空间** —— 检索失准，**依然不报错**。症状与 digest 不一致完全相同，但原因不同，排查时极易混淆。

**规避：两边都用 Ollama 同一个 digest，都走默认行为。** 绝不要一边 Ollama、一边自己写 Python 调 transformers —— 那样前缀、归一化、池化方式都可能不同。

### 4.5 召回验证

| 步骤 | 做法 |
|---|---|
| 1 | 找 10–20 条公开申报书素材，导入 Dify 知识库 |
| 2 | 出 20–30 道题（问题 → 期望命中条目），**这就是测试集** |
| 3 | 逐题查召回，算召回率 |
| 4 | 及格线 **≥ 90%**；不达标先修知识库，别急着调工作流 |
| 5 | （可选）同批素材用 `bge-large-zh-v1.5` 再索引一遍对比 |

**测试集要留着。** 每次知识库更新后重跑，否则不知道改进有没有效。
