# 技术架构说明

> 本文档描述系统全貌：编排、变量、知识库、代码节点、输出、触发、监控、记忆。
> 单个节点的内部细节（提示词、审查项、参数）见 `docs/WORKFLOW.md`。
> 硬件与选型论证见 `docs/技术选型.md`。

---

## 一、总体架构

```
企业素材 ──┐
           ├──► Dify 工作流 ──► Markdown 初稿 ──► 人工审核 ──► DOCX ──► 提交
知识库  ───┘         │
                     └── 全程本地，数据不出内网
```

### 分层

| 层 | 组件 | 职责 | 本地化 |
|---|---|---|---|
| 输入层 | Dify 应用表单 + 文件上传 | 收集 10 个输入变量与申报指南 | ✅ |
| 编排层 | Dify 工作流引擎 | 节点调度、变量传递、流程控制 | ✅ 本地 Docker |
| 知识层 | Dify 内置 RAG | 三类知识库检索 | ✅ 本地向量库 |
| 推理层 | Ollama / vLLM + 量化模型 | 章节正文生成 | ⚠️ **可外置** —— 见 1.1 |
| 校验层 | 代码执行节点 | 要素抽取、变量替换、分块、一致性 | ✅ |
| 输出层 | Markdown → DOCX | 套官方模板排版 | ✅ |
| 调度层 | Schedule Trigger / XXL-JOB | 定时、Webhook、手动触发 | ✅ |
| 观测层 | Dify Logs + XXL-JOB Dashboard | 运行记录、告警 | ✅ |
| 记忆层 | 运行时 Agent 记忆 `memory/` + 本地记忆服务 | Agent 跨会话记忆、知识库缺口反馈 | ✅ |

**核心约束：整条链路不调用第三方 API。** 这是对企业技术秘密的承诺，不是技术偏好。

### 1.1 部署拓扑（三机形态）★

目标运行机**显存仅 1GB**，跑不了任何本地模型（7B Q4 需 ~6GB）。因此推理层与编排层必须解耦。

```
目标机（1GB 显存）                     推理机（有 GPU 的任何地方）
┌─────────────────────┐                ┌──────────────────────┐
│ Dify 工作流引擎      │   HTTP 调用    │ Ollama / vLLM        │
│ 向量库（CPU）        │ ──────────────►│ 量化模型              │
│ 记忆服务             │                │                      │
│ XXL-JOB 执行器       │                │                      │
└─────────────────────┘                └──────────────────────┘
```

| 阶段 | 编排层 | 推理层 |
|---|---|---|
| 开发验证 | 开发机（Mac / 独显机） | 同机（Mac 走 Metal，独显走 CUDA） |
| 交付运行 | 目标机（1GB 显存，CPU 足够） | **外置** |

**配置方式：** 推理机设 `OLLAMA_HOST=0.0.0.0` 暴露服务，Dify 模型接入填其 URL。**代码零改动。**

**Embedding 也走 CPU。** bge 系列在 CPU 上索引可接受（批量入库慢，单次查询 ~100ms）。1GB 显存连 embedding 都放不下。

**推理机候选（按合规性排序）：**

| 候选 | 数据边界 | 成本 | 状态 |
|---|---|---|---|
| 局域网内 GPU 服务器 | ✅ 不出内网 | 看有无现成 | **首选，待确认** |
| 云 GPU 实例 | ⚠️ 出内网，但在专属实例 | ¥2–3/小时 | 备选 |
| 云 API | ❌ 进第三方日志 | 低 | 不建议 |

> ⚠️ **若推理走上云，"数据不出内网"的承诺需重新定义**，并重新与企业沟通。见 `CLAUDE.md` 第八节。

## 二、Dify 节点编排图

```
[开始]
   │  输入 10 个变量（见第三节）
   ▼
[文档提取器]  ← reference_files（申报指南 / 项目文档）
   │  解析：申报要求、模板结构、评审要点
   ▼
[知识检索]  ← 绑定 6 个知识库（见第四节）
   │  分渠道召回：模板类 / 素材类 / 风格类
   ▼
[代码执行节点 ①  · 要素抽取]
   │  一次性抽全局要素表：人员 / 预算 / 周期 / 核心指标 / 知识产权
   │  产出 gen_elements —— 后续所有章节的硬约束
   ▼
[迭代节点]  逐章节生成
   │  ├─ LLM · 项目背景
   │  ├─ LLM · 技术方案
   │  ├─ LLM · 实施计划
   │  ├─ LLM · 团队基础
   │  ├─ LLM · 预期成果
   │  ├─ LLM · 经费预算
   │  └─ LLM · 风险应对
   ▼
[代码执行节点 ②  · 变量替换 + 长文档分块]
   │  套 templates/ 模板，填占位符
   ▼
[代码执行节点 ③  · 一致性审查]
   │  数字回溯 / 章节间一致 / 必填齐全 / 占位符残留
   ▼
[条件分支]
   ├─ 不通过 ──► 回退问题章节重生成（上限 2 次）
   └─ 通过 ──► [HTTP 节点 · DOCX 转换]
   ▼
[结束]  文件下载
```

### 为什么要素抽取单独成节点

长文档分块生成最大的坑是**章节间自相矛盾**：背景章节写投入 8 人，团队章节写 12 人。

解法：先生成一次全局要素表，所有章节共享同一份，且提示词声明为硬约束。从结构上消除分歧，比事后审查可靠。

## 三、输入变量清单

开始节点定义，共 10 个。

| # | 变量名 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| 1 | `declaration_type` | 下拉选择 | 是 | 申报类型：高新技术企业认定 / 科技型中小企业创新基金 |
| 2 | `project_name` | 文本 | 是 | 项目名称 |
| 3 | `tech_direction` | 文本 | 是 | 技术方向 |
| 4 | `project_leader` | 文本 | 是 | 项目负责人 |
| 5 | `team_size` | 数字 | 是 | 投入人数 |
| 6 | `budget_range` | 文本 | 是 | 预算规模 |
| 7 | `expected_outcome` | 多行文本 | 是 | 预期成果 |
| 8 | `project_highlights` | 多行文本 | 是 | 项目亮点 |
| 9 | `special_requirements` | 多行文本 | 否 | 特殊要求 |
| 10 | `reference_files` | 文件上传 | 否 | 申报指南 / 项目文档 |

### 内部变量命名规则

| 前缀 | 含义 | 例 |
|---|---|---|
| `in_` | 用户输入 | `in_project_name` |
| `kb_` | 知识库召回 | `kb_template` |
| `gen_` | 模型/代码生成 | `gen_section_tech` |
| `chk_` | 校验结果 | `chk_report` |

**模板占位符与变量同名。** `templates/申报书模板.md` 中 `{{gen_section_tech}}` 即对应此处变量。

## 四、知识库绑定关系

### 4.1 六个知识库 → 节点绑定

| # | 知识库 | 类型 | 检索用途 | 绑定节点 |
|---|---|---|---|---|
| 1 | 模板-科技型中小企业 | 模板 | 章节骨架、评分要点 | 知识检索 |
| 2 | 模板-高新技术企业 | 模板 | 章节骨架、评分要点 | 知识检索 |
| 3 | 素材-企业技术参数 | 素材 | **事实来源** | 知识检索 + 代码节点① |
| 4 | 素材-知识产权 | 素材 | 专利 / 软著清单 | 知识检索 + 代码节点① |
| 5 | 素材-财务数据 | 素材 | 预算、营收 | 知识检索 + 代码节点① |
| 6 | 风格-优秀申报书 | 风格 | 语体、措辞、论证结构 | 知识检索 |

### 4.2 分渠道召回

三个渠道**不可混检**。混检会导致"问技术方案怎么写，召回企业财务数据"。

| 渠道 | 检索方式 | 用途 | 去向 |
|---|---|---|---|
| 模板渠道 | 按 `declaration_type` 精确匹配 | 定章节结构 | 迭代节点（决定生成哪些章节） |
| 素材渠道 | 混合检索（向量 + 关键词），top-k 3–5 | 提供事实 | 代码节点① + 各章节 LLM |
| 风格渠道 | 按章节类型语义检索 | 提供表达 | 各章节 LLM |

### 4.3 检索参数

| 项 | 值 | 状态 |
|---|---|---|
| 检索模式 | 混合检索（向量 + 关键词） | 定 |
| top-k | 3–5 | 待实测 |
| 相似度阈值 | 待实测 | |
| Rerank | 待定，建议启用 | |
| Embedding 模型 | **待与 B 确认** ⚠ | 一次定死 |

### 4.4 硬约束

**素材类知识库是唯一事实来源。** `gen_section_*` 中的每个数字必须能回溯到 `kb_material` 条目。代码节点③ 负责执行这条约束。

知识库建设方法（分块策略、元信息规范、检索测试）见 `knowledge/README.md`。

## 五、代码执行节点逻辑

三个代码节点，脚本存放 `scripts/`，函数入口 `main()`，仅用标准库。

### 节点 ① `extract_elements.py` — 要素抽取

**作用：** 把散落的素材条目结构化为一份全局要素表，作为所有章节的硬约束。

**输入：** `kb_material`（技术参数 / 知识产权 / 财务数据三库召回结果）

**输出：** `gen_elements`

```json
{
  "project_name": "…",
  "team_size": 8,
  "duration_months": 24,
  "total_budget": 500,
  "budget_breakdown": {"设备费": 200, "材料费": 100, "…": 0},
  "core_metrics": [
    {"name": "检测精度", "target": "99.2%", "baseline": "97.0%", "source": "2024检测报告"}
  ],
  "ip_list": [
    {"type": "发明专利", "count": 3, "status": "已授权", "numbers": ["ZL…"]}
  ],
  "missing": ["2024年度研发投入金额及占营收比例"]
}
```

**逻辑要点：**

1. 从召回文本中抽取结构化字段，**不做任何推算**
2. 抽不到的字段进 `missing` 数组，不填默认值、不填估值
3. 每个数值附带 `source` 字段，指回素材条目 —— 这是节点③ 回溯校验的依据
4. 数字原样保留，不做四舍五入、不做单位换算（避免精度损失与二次错误）

**为什么不用 LLM 做这一步：** 抽取要求确定性，LLM 有概率改写数字。结构化抽取用规则 + 正则，LLM 只在纯文本段落上兜底。

---

### 节点 ② `fill_template.py` + `chunk_document.py` — 变量替换与分块

**作用：** 把各章节生成结果套入模板，并控制上下文长度。

**输入：** `gen_section_*`、`gen_elements`、`templates/申报书模板.md`

**输出：** `gen_document`（完整 Markdown）

**逻辑要点：**

1. 逐个替换 `{{var}}` 占位符
2. **替换后扫描是否有残留 `{{`** —— 有则记入 `issues`，交节点③
3. 表格类占位符按 `gen_elements` 的数组长度动态生成行
4. 长文档若超出模型上下文，按章节边界分块串行生成（**不在段落中间切**，避免语义割裂）
5. 表格、代码块等结构块**不跨块切分**

**分块原则：** 按语义边界（章节 / 段落）切，不按固定字数硬切。硬切会产生"上半句说 A，下半句说 B"的碎片，检索到也无法使用。

---

### 节点 ③ `check_consistency.py` — 一致性审查

**作用：** 生成后校验，决定是否回退重生成。

**输入：** `gen_document`、`gen_elements`、`kb_material`

**输出：** `chk_report`

```json
{
  "pass": false,
  "issues": [
    {"type": "number_mismatch", "section": "团队基础", "detail": "人员数 12 与要素表 8 不符", "severity": "block"},
    {"type": "unresolved_placeholder", "section": "经费预算", "detail": "残留 {{gen_budget_item}}", "severity": "block"},
    {"type": "fabricated_qualification", "section": "-", "detail": "专利号 ZL… 在素材中不存在", "severity": "block"},
    {"type": "missing_data", "section": "预期成果", "detail": "【待补充】3 处，需人工补全", "severity": "warn"}
  ],
  "stats": {"tbd_count": 3, "word_count": {"技术方案": 1820}, "blocking": 3, "warnings": 1}
}
```

**`severity` 与 `stats` 是实现的扩展**（原契约只有 type/section/detail）。条件分支节点
直接读 `pass` —— `pass` 只看 `block` 级，`warn` 级放行交人工。等级划分见 `scripts/README.md`。

**七项检查：**

| # | 检查项 | 判定方式 |
|---|---|---|
| 1 | 全局数字一致 | 与 `gen_elements` 逐项比对 |
| 2 | 数字可回溯 | 正文每个数字在 `kb_material` 中命中 |
| 3 | 无杜撰资质 | 专利号 / 证书号 / 报告编号可溯源 |
| 4 | 占位符无残留 | 扫描 `{{` |
| 5 | 空缺统计 | 统计 `【待补充】` 数量并提示人工 |
| 6 | 章节字数达标 | 各章节在要求区间 |
| 7 | 风格未串事实 | 检测风格库中的企业名 / 数据是否混入 |

**约定：不抛异常中断流程。** 返回结构化结果，由条件分支节点判断。脚本异常中断会导致整个工作流失败，无法定位问题。

**回退策略：** 仅回退到问题章节，不整篇重生成。上限 2 次，超过则带 `issues` 输出，交人工。

## 六、输出链路（Markdown → DOCX）

### 6.1 链路

```
各章节 LLM 输出
   ▼
代码节点② 套模板
   ▼
gen_document（完整 Markdown）
   ▼
一致性审查通过
   ▼
HTTP 节点  ──►  Markdown to DOCX 服务
   ▼
{project_name}_申报书_初稿.docx
   ▼
Dify 文件存储 ──► 结束节点返回下载链接
```

### 6.2 两种方案

| 方案 | 说明 | 优先级 |
|---|---|---|
| **Markdown to DOCX 插件** | Dify 插件市场现成，HTTP 节点调用 | 首选 |
| **自建 python-docx API** | 本地起服务，HTTP 节点调用，排版完全可控 | 备选 |

**何时切换到自建：** 插件无法满足官方模板的排版要求（字体、页边距、页眉页脚、表格样式）时。申报系统的格式要求通常很具体，插件大概率需要二次调整。

### 6.3 排版要求来源

官方申报模板的样式要求从两个渠道获取：

1. `reference_files` 上传的申报指南（文档提取器解析）
2. `templates/` 下的 Markdown 模板（人工按官方模板反向映射）

**阶段一先用官方模板反向定 Markdown 结构**，确保章节顺序、必填项与官方一致，再谈排版细节。

### 6.4 输出规范

| 项 | 要求 |
|---|---|
| 文件名 | `{project_name}_申报书_初稿.docx` |
| 版本标记 | `初稿` 字样不可省略，提醒未经审核 |
| 头部声明 | "本稿件由 AI 生成初稿，数据未经核实，请逐项核对后使用。" |
| 中间产物 | `gen_document` 同步存 Markdown，便于 diff 与二次编辑 |
| 下载有效期 | 注意 Dify 文件链接有效期，及时下载 |

### 6.5 风险

| 风险 | 应对 |
|---|---|
| 插件排版不达官方要求 | 预留给自建 python-docx 的时间（第 2 周 D10） |
| 表格跨页 / 错位 | 用 Word 样式而非直接格式化，交由 DOCX 层处理 |
| 中文字体缺失 | 服务端安装常用中文字体 |
| 文件过大 | 图片单独走附件，不内嵌 |

## 七、触发器配置

三种触发方式并存，服务于不同场景。

### 7.1 手动触发（默认）

| 项 | 内容 |
|---|---|
| 方式 | Dify 应用界面直接填写表单 → 运行 |
| 场景 | 开发调试、单次生成、培训演示 |
| 认证 | 登录 Dify 账号 |
| 状态 | **阶段一主用** |

### 7.2 Webhook / API 触发（企业集成）

| 项 | 内容 |
|---|---|
| 方式 | 调 Dify 工作流 API |
| 端点 | `POST {DIFY_BASE}/v1/workflows/run` |
| 认证 | `Authorization: Bearer app-xxxx`（工作流 API Key） |
| 请求体 | `{"inputs": {...10个变量...}, "response_mode": "blocking", "user": "<企业标识>"}` |
| 模式 | `blocking` 直接返回结果；`streaming` 流式返回（生成耗时长，推荐） |
| 文件传参 | 先调 `POST /v1/files/upload` 拿 `upload_file_id`，再作为 `reference_files` 传入 |
| 场景 | 企业自有系统（OA / 项目管理）集成 |
| 状态 | 阶段二 |

**注意：** 生成耗时 20–40 分钟，超出多数 HTTP 客户端默认超时。企业侧集成必须用 `streaming` 模式或轮询任务状态，不能指望同步阻塞返回。

### 7.3 定时触发（批量）

| 方案 | 说明 | 优先级 |
|---|---|---|
| Dify Schedule Trigger | 工作流内置定时节点 | 首选（若版本支持） |
| XXL-JOB | 独立调度中心，调 Dify API | 备选，功能更全 |

**XXL-JOB 配置要点：**

| 项 | 说明 |
|---|---|
| 执行器 | 部署在执行器节点，注册到调度中心 |
| 任务 | 每任务对应一个申报类型 / 一批企业 |
| 调度 | Cron 表达式，避开业务高峰 |
| 失败策略 | 失败重试 1–2 次；连续失败告警 |
| 分片 | 批量企业可分片并行（受显存限制，实际串行） |
| 场景 | 申报季批量处理 |
| 状态 | 第 3 周 D11 |

**为什么需要 XXL-JOB 而非只用 Dify：** 调度中心提供任务级别的失败重试、执行日志、告警、手动触发/终止，Dify 自身只管单次工作流运行。批量场景需要调度层的可观测性。

### 7.4 触发方式对比

| | 手动 | Webhook | 定时 |
|---|---|---|---|
| 触发者 | 人 | 外部系统 | 调度器 |
| 认证 | Dify 登录 | API Key | 调度中心 |
| 时延要求 | 无 | 异步 | 无 |
| 阶段 | 一 | 二 | 二/三 |

## 八、监控与告警方案

### 8.1 观测来源

| 来源 | 提供什么 |
|---|---|
| **Dify Logs** | 每次运行记录、节点级耗时、Token 消耗、失败原因、输入输出快照 |
| **XXL-JOB Dashboard** | 调度成功/失败、执行日志、任务耗时趋势 |
| **一致性审查报告** `chk_report` | 生成质量指标（`【待补充】` 数量、字数、回退次数） |
| **人工审核反馈** | 修改率 —— 最终质量指标 |

### 8.2 告警规则

| # | 规则 | 阈值 | 级别 |
|---|---|---|---|
| 1 | 工作流运行失败 | 任一失败 | 高 |
| 2 | 单次生成超时 | > 60 分钟 | 高 |
| 3 | 连续失败 | ≥ 2 次 | 高 |
| 4 | 知识库检索命中为空 | 素材渠道 top-k 全空 | 高（知识库可能未绑定或素材缺失） |
| 5 | 模型服务不可用 | Ollama 健康检查失败 | 高 |
| 6 | 显存不足 | OOM 报错 | 高 |
| 7 | 回退次数触顶 | 连续 2 次审查不通过 | 中 |
| 8 | `【待补充】` 占比过高 | > 15% 章节内容 | 中（知识库缺口信号） |
| 9 | 单份耗时劣化 | 超过基线 1.5 倍 | 低 |
| 10 | 每日生成量为 0 | 定时任务未触发 | 中 |

### 8.3 告警渠道

| 渠道 | 适用 | 说明 |
|---|---|---|
| 邮件 | 全部告警 | XXL-JOB 内置支持 |
| 企业微信机器人 | 高优先级 | Webhook 推送，及时 |
| 钉钉机器人 | 高优先级 | 同上，按团队习惯选一 |
| Dify 界面 | 被动查看 | 不作为主动告警手段 |

### 8.4 质量指标（长期跟踪）

这几项不触发告警，但决定项目成败。人工每周记录。

| 指标 | 算法 | 目标 |
|---|---|---|
| **人工修改率** ★ | 人工改动字数 / 总字数 | < 30% |
| 生成可用率 | 修改率 < 30% 的稿件占比 | ≥ 70% |
| 平均生成耗时 | 运行日志统计 | 20–40 分钟 |
| `【待补充】` 密度 | 每千字标注数 | 持续下降 |
| 回退率 | 触发回退的运行占比 | < 20% |

**人工修改率是唯一真实的质量指标。** 其他指标都是它的代理。修改率高，说明知识库素材不足或提示词不到位 —— 回写 `lessons.md`。

### 8.5 日志留存

| 项 | 要求 |
|---|---|
| 运行日志 | 保留 ≥ 90 天 |
| 生成结果 | 保留中间产物 `gen_document`，便于复盘 |
| 敏感素材 | 日志中不得残留企业敏感原文，按需脱敏 |
| 备份 | 知识库与工作流配置定期导出（见 `dify/README.md`） |

## 九、Harness 记忆系统设计

### 9.1 定位

`memory/` 是**运行时申报书 Agent 的记忆**，由该 Agent 通过 5 个记忆工具读写。

| 角色 | 与 memory/ 的关系 |
|---|---|
| **申报书 Agent（运行时）** | ✅ 读写 —— 记忆的主人 |
| Claude Code（开发时） | ❌ 不写。只设计、调试、验证记忆系统 |
| 人工 | 可直接编辑（Markdown，人类可读） |

**为什么分开：** Claude Code 与申报书 Agent 是两套东西。前者是开发工具，后者是被开发的产品。混在一起会导致记忆内容里既有开发笔记又有运行经验，两者都失去可用性。

因此：**开发进度与待办记 `CLAUDE.md`「当前任务」，不记 `memory/CONTEXT.md`。**

### 9.2 实现桥梁：本地记忆服务 ⚠

**问题：** Dify 的 LLM 节点访问不到本地文件系统，代码节点沙箱也不保证可持久读写。Agent 想写 `memory/`，缺一条通路。

**方案：** 把 5 个记忆工具做成**本地 HTTP 服务**，Dify 用 HTTP 节点调用。

```
Dify 工作流
   │
   ├─ 生成完成 ──► HTTP 节点 ──► POST /memory/write  {"file": "decisions.md", ...}
   │
   └─ 生成开始 ──► HTTP 节点 ──► POST /memory/read   {"file": "lessons.md"}
                                        │
                                        ▼
                              本地记忆服务（FastAPI）
                                        │
                                        ▼
                                 memory/*.md
```

| 端点 | 对应工具 | 用途 |
|---|---|---|
| `POST /memory/read` | `memory_read` | 读取文件 |
| `POST /memory/write` | `memory_write` | 覆盖 / 追加写入 |
| `POST /memory/replace` | `memory_replace` | 替换片段（0 处或多处匹配报错，不静默） |
| `POST /memory/insert` | `memory_insert` | 插入条目（按文件有默认落点） |
| `GET /memory/list` | `memory_list` | 列出文件 |
| `POST /memory/rollback` | — | 从备份恢复（契约外补充） |
| `GET /memory/inject` | — | 返回 CONTEXT + AGENTS 拼接文本，供系统提示词注入 |

**实现：** `memory_service/`（FastAPI）。完整契约见 `memory_service/README.md`。

| 端点 | 请求体关键字段 | 说明 |
|---|---|---|
| `POST /memory/read` | `file` | 返回 `content` / `bytes` / `lines` / `mtime` |
| `POST /memory/write` | `file` `content` `mode`(overwrite\|append) | |
| `POST /memory/replace` | `file` `old` `new` `allow_multiple` | 匹配 0 处或 >1 处**报错**，不静默 |
| `POST /memory/insert` | `file` `content` `anchor` `position` | decisions 默认插首条前，lessons 默认插「## 已记录」后 |
| `GET /memory/list` | — | |
| `GET /memory/inject` | — | CONTEXT + AGENTS 拼接 |

写操作通用可选字段：`actor`（写进审计）、`dry_run`（只回报 diff，不落盘）。
失败统一 `{"ok": false, "error": {"code", "message"}}` + HTTP 状态码，
**条件分支节点读 `error.code`，不解析 message**。

**约束（实现时落实为代码，不是口头约定）：**

- 默认只监听 `127.0.0.1`；**无令牌时绑非本机地址拒绝启动**。
  记忆文件会注入 system prompt，暴露到局域网等于交出提示词注入入口
- 文件名**白名单精确匹配**，不做路径拼接 —— `../`、`a/b`、绝对路径一律 `unknown_file`
- 写前备份到 `memory/.backups/`（保留最近 20 份），配 `/memory/rollback` 恢复
- 临时文件 + `os.replace` 原子写；只有「读—改—写」复合操作加锁（线程锁 + `fcntl`）
- 每次写操作追加一行 `memory/.audit.jsonl`，供远程监看与追责
- 与 Dify 同机部署，不起额外容器网络开销

**落地时机：** 第 2 周 D8–D10，与代码执行节点同期。✅ 已实现（51 项单测）。

### 9.3 四个文件

| 文件 | 内容 | 注入方式 | 更新频率 |
|---|---|---|---|
| `CONTEXT.md` | Agent 身份、支持的申报类型、知识库位置、输出格式、人工审核项 | **Agent 启动时注入 system prompt** | 规则/范围变更时 |
| `AGENTS.md` | 行为规则：必须做 / 禁止做 / 记忆写入规则 | Agent 启动时注入 | 规则变更时（罕见） |
| `decisions.md` | 每次生成后的关键决策：用了哪些素材、做了哪些取舍 | 按需读取 | 每次生成 |
| `lessons.md` | 人工修改后的经验教训、知识库缺口 | 按需读取 | 每次人工修改 |

> **开发进度与待办不在 `memory/` 里**，在 `CLAUDE.md`「当前任务」。见 9.1。

### 9.4 五个记忆工具

实现为本地记忆服务的 HTTP 端点（见 9.2）。

| 工具 | 用途 | 端点 | 典型场景 |
|---|---|---|---|
| `memory_read` | 读取记忆文件 | `POST /memory/read` | 生成前回顾历史决策 |
| `memory_write` | 写入 / 覆盖 | `POST /memory/write` | 生成后写决策 |
| `memory_replace` | 替换片段 | `POST /memory/replace` | 更新单条而不动全文件 |
| `memory_insert` | 插入条目 | `POST /memory/insert` | 追加新条目（倒序，最新在上） |
| `memory_list` | 列出文件 | `GET /memory/list` | 确认现有记忆范围 |

### 9.5 读写时机

| 时机 | 动作 | 目标文件 | 触发方 |
|---|---|---|---|
| Agent 启动 | 注入 CONTEXT + AGENTS | — | 系统提示词装配 |
| 生成开始前 | 读取历史决策供参考 | `decisions.md` | HTTP 节点 |
| **生成完成后** | 写入本次用了哪些素材、做了哪些取舍 | `decisions.md` | HTTP 节点 |
| **人工修改成稿后** | 写入修改原因与改进方向 | `lessons.md` | HTTP 节点 / 人工 |
| 发现知识库缺口 | 标注需补充的素材类型 | `lessons.md` | HTTP 节点 |
| **每周复盘** | 汇总 `lessons.md` 高频问题 → 通知 B 补素材 | 汇总输出 | 人工 + Claude Code |

### 9.6 每周复盘机制

这是记忆系统闭环的关键环节。

```
人工修改成稿
   ▼
lessons.md 逐条记录
   ▼
每周汇总：统计高频问题
   ▼
分类归因
   ├─ 知识库缺口 ──► 通知 B 补充素材
   ├─ 提示词问题 ──► 同类问题 ≥ 2 次则改 dify/prompts/
   └─ 流程问题   ──► 改工作流，记 decisions.md
   ▼
下一轮生成验证效果
```

**没有复盘，记忆就只是日志。** 闭环才算记忆系统。

复盘由人工完成，Claude Code 可协助汇总分析（读 `lessons.md` → 归因 → 生成给 B 的素材清单），但不代写记忆内容。

### 9.7 记录格式

`lessons.md` 每条：

| 字段 | 说明 |
|---|---|
| 日期 | YYYY-MM-DD |
| 章节 | 哪个章节出的问题 |
| 现象 | 原文怎么写的，错在哪 |
| 原因 | 素材缺失 / 提示词不到位 / 知识库没有 |
| 修正 | 人工改成了什么 |
| 规避 | 改提示词 / 补素材 / 加校验 |

**记忆文件是人类可读的 Markdown**，可直接手工编辑，不依赖工具。
