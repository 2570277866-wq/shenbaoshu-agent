# 项目计划书

## 一、项目定位与核心原则

### 1.1 定位

为科创企业搭建**本地部署、可自动执行、可远程监看、可扩充**的项目申报书自动撰写 AI Agent。

处理的是"有素材但写不动"的场景：企业手里有技术、有数据、有案例，缺的是把散落信息组织成符合评审口味的申报文本的能力。Agent 补的正是这一段。

### 1.2 核心原则

| 原则 | 含义 | 违反后果 |
|---|---|---|
| **AI 出初稿，人工做审核** | Agent 产出的是初稿，对外提交前必须经人审 | 未审提交＝企业担责 |
| **不编造数据** | 缺材料时明确标注"待补充"，不猜不凑 | 申报书造假，法律与信誉风险 |
| **数据不出内网** | 全本地部署，素材不经过第三方 API | 企业技术秘密外泄 |
| **知识库是唯一事实来源** | 正文中的数字、指标、资质必须可回溯到知识库条目 | 无法溯源＝不可信 |
| **人可读可改** | 模板、记忆、配置全部 Markdown | 企业方无法自行维护 |

### 1.3 不做什么（划边界）

- 不做申报策略咨询 —— Agent 是写作工具，不是申报顾问
- 不做材料真伪核验 —— 假设 B 提供的素材真实
- 不做在线协作编辑 —— 输出交付后由企业自行修改
- 不替代专业代理机构 —— 与代理机构是工具关系，非竞争关系

## 二、三阶段落地路径

### 阶段一：单点突破（当前）

**目标：** 跑通一个申报类型的端到端生成，证明链路可行。

| 项 | 内容 |
|---|---|
| 范围 | 1 个申报类型（建议：科技型中小企业），全部章节 |
| 用户 | 内部试用，A + B 自己跑 |
| 交付 | 3 份真实项目生成样稿 + 人工评审意见 |
| 成功标准 | 输出可用率 ≥ 70%（人工修改量 < 30%） |
| 周期 | 20–30 个工作日 |

**不做：** 多租户、计费、审批流、自动调度到企业。

### 阶段二：场景扩展

**目标：** 覆盖多申报类型，接入真实企业用户。

| 项 | 内容 |
|---|---|
| 新增 | 高新技术企业等多个申报类型模板 |
| 新增 | DOCX 排版输出、附件自动生成 |
| 新增 | 自动调度（Schedule Trigger），支持定时批量生成 |
| 新增 | 企业侧操作表单，非技术人员自助使用 |
| 成功标准 | ≥ 3 家企业实际使用，累计 ≥ 20 份申报书 |

**触发条件：** 阶段一可用率达标，且至少 2 家意向企业愿意提供真实素材。

### 阶段三：平台化

**目标：** 从"给企业用的工具"变成"能持续沉淀知识的平台"。

| 项 | 内容 |
|---|---|
| 沉淀 | 每次人工修改回写为经验，风格库持续增强 |
| 横向 | 扩展到其他公文类型（项目结题、成果鉴定、专利交底书） |
| 数据 | 建立素材-成稿对照库，用于效果度量与迭代 |
| 商业 | 明确交付形态（私有化交付 / SaaS / 混合） |

**前提：** 阶段二积累了足够的真实修改数据。没有数据就没有平台，只有工具。

## 三、执行排期（20–30 个工作日）

按 4 周规划，每周 5 个工作日。带 ⚠ 的是关键路径，延误会顺延后续全部。

### 第 1 周：环境与最小链路

| 日 | 任务 | 产出 | 依赖 |
|---|---|---|---|
| D1 | Docker Compose 部署 Dify；目录结构初始化 | Dify 可访问 | 硬件到位 ⚠ |
| D2 | Ollama 拉取量化模型，Dify 接入并验证对话 | 模型可用 | D1 ⚠ |
| D3 | 确定 Embedding 模型，与 B 对齐版本 | 模型型号确认 | B ⚠ |
| D4 | 建空白工作流：开始 → 知识检索 → LLM → 结束 | 最小链路 | D2 ⚠ |
| D5 | 单章节（技术方案）生成跑通 | 首个生成结果 | 知识库有素材 ⚠ |

**周末检查点：** 模型能跑、能检索、能出文。任一不满足 → 第 2 周先补，不加新功能。

### 第 2 周：完整工作流与自动化

| 日 | 任务 | 产出 |
|---|---|---|
| D6–D7 | 扩展多章节 LLM 节点（背景/方案/计划/团队/成果/预算/风险） | 全章节生成 |
| D8 | 代码执行节点：变量替换、长文档分块 | `scripts/` 脚本 |
| D9 | 一致性审查节点（交叉校验章节间数字与表述） | 审查节点 |
| D10 | 接入 Markdown to DOCX；启用迭代节点处理长文档 | DOCX 输出 |

### 第 3 周：监控 + 触发 + 测试

| 日 | 任务 | 产出 |
|---|---|---|
| D11 | 部署 XXL-JOB 或配置 Dify API 触发 | 触发通道 |
| D12 | 配置日志与告警 | 可观测 |
| D13–D14 | 用 3 个真实项目测试 | 3 份样稿 |
| D15 | 建立记忆回写机制（人工修改 → lessons.md） | 闭环 |

**关键节点：** D13–D14 的测试结果决定项目是否继续。3 份样稿若均需推倒重写，说明知识库或提示词方向错了，回第 2 周重做，不要硬推到交付。

### 第 4 周：包装与交付

| 日 | 任务 | 产出 |
|---|---|---|
| D16 | Dify 应用输入表单配置（10 个输入变量） | 可用表单 |
| D17–D18 | 编写使用指南 + 培训材料 | `docs/使用指南.md` |
| D19 | 企业培训 | 培训完成 |
| D20 | 交付、验收、遗留问题清单 | 验收单 |

### 缓冲

20 个工作日为紧凑版，30 个工作日为含缓冲版。缓冲优先给：第 1 周环境问题、第 3 周测试返工、知识库素材延迟。

## 四、压缩版 Demo 方案（7–10 天）

**用途：** 立项汇报、领导演示、争取资源。目标不是可用系统，是**证明方向可行**。

### 砍掉什么

| 砍掉 | 理由 | 演示时怎么交代 |
|---|---|---|
| 多申报类型 | 只留科技型中小企业 | "模板可扩展，现有 1 套跑通" |
| 多章节 | 只做 2 章：技术方案 + 预期成果 | "章节节点是复制关系，非技术风险" |
| DOCX 输出 | 先出 Markdown | "排版层是独立插件，不影响核心链路" |
| 自动调度 | 手动点击触发 | "触发器已预留接口" |
| 一致性审查 | 无 | "下一步重点，需要人工参与验证" |
| 企业表单 | 用 Dify 自带调试表单 | "输入变量已定义 10 个" |

### 保留什么（不可砍）

1. **本地部署** —— 这是核心卖点，绝不能退化成调 API
2. **知识库检索** —— 没有 RAG 就只是个套壳聊天，必须展示"检索到企业专属素材"
3. **真实企业素材** —— 演示必须用真实项目数据，用假数据等于没演示
4. **人工审核环节** —— 明确定位为"AI 初稿"，别吹成全自动

### 时间分配

| 天 | 任务 |
|---|---|
| D1 | 环境部署 + 模型接入 |
| D2–D3 | 知识库导入（精简版：模板 1 类 + 素材 3 类 + 风格 1 类） |
| D4–D5 | 两章节工作流搭建 + 提示词调优 |
| D6 | 端到端联调 |
| D7 | 用 1–2 个真实项目出样稿，准备演示脚本 |
| D8–D10 | 缓冲 / 汇报材料 / 演示彩排 |

### 演示脚本要点

- 现场改一个输入变量 → 重跑 → 展示输出跟着变（证明是体系不是模板填空）
- 展示检索命中：让企业看到"这句话来自你们 2023 年的检测报告"
- 主动说局限：硬件、章节数、审核要求 —— 降低预期反而更可信

## 五、关键风险与应对

按"后果严重度 × 发生概率"排序。

### R1 模型幻觉编造数据 ⚠⚠⚠

| | |
|---|---|
| **后果** | 申报书出现不存在的专利号、虚高营收、杜撰的检测指标 → 企业被取消资格甚至追责 |
| **概率** | 高。所有 LLM 都有此倾向，本地小模型更明显 |
| **应对** | ① 提示词硬约束：无素材时输出 `【待补充：xxx】`；② 代码执行节点做数字回溯校验，正文出现的每个数字必须在知识库中命中；③ 一致性审查节点独立复核；④ 人工审核为法定环节，写入使用指南 |
| **兜底** | 生成结果页固定显示"本稿件由 AI 生成初稿，数据未经核实，请逐项核对" |

### R2 硬件不足，模型跑不动或太慢 ⚠⚠⚠

| | |
|---|---|
| **后果** | 32B 模型长上下文爆显存；或生成一份申报书耗时过长，体验崩坏 |
| **应对** | 先实测再定模型档位；准备降级方案（14B）；长文分块串行生成而非一次塞入 |
| **决策点** | 第 1 周 D2 必须定性：能跑什么模型、单章节耗时多少。不达标立刻上报，不硬扛 |

### R3 知识库素材不到位（依赖 B）⚠⚠

| | |
|---|---|
| **后果** | 第 1 周 D5 无法完成单章节生成，全线顺延 |
| **应对** | D3 前必须拿到最小素材集（1 类模板 + 3 类素材 + 1 类风格）；素材未到位时先用公开范文搭架子，后替换 |
| **责任** | B。A 不代劳知识库内容（CLAUDE.md 明确约束） |

### R4 Embedding 模型不一致 ⚠⚠

| | |
|---|---|
| **后果** | A 用一套、B 用另一套建索引 → 检索结果完全失准，且症状隐蔽（能跑通，但召回差） |
| **应对** | D3 书面确认型号与版本，写入 `memory/decisions.md`；更换需全库重建，成本高，一次定死 |

### R5 长文档分块后章节间不一致 ⚠⚠

| | |
|---|---|
| **后果** | 背景章节说投入 8 人，团队章节写 12 人；预算与技术方案对不上 |
| **应对** | 一次性抽取项目要素表（人员/预算/周期/指标）作为全局变量，各章节生成时统一注入，禁止各章节各自编 |

### R6 Dify 版本升级破坏工作流 ⚠

| | |
|---|---|
| **后果** | 升级后节点行为变化、导出文件不兼容，返工 |
| **应对** | 锁定版本；每次改动导出 `dify/workflow_vX.Y.yml` 入库；升级前先备份 + 跑回归测试 |

### R7 人工审核被跳过 ⚠

| | |
|---|---|
| **后果** | 未审初稿直接提交 → 风险回到 R1 |
| **应对** | 交付物文件名带 `_DRAFT` 后缀；使用指南开篇写明审核要求；培训时现场演示一遍审核清单 |

### R8 交付格式不满足申报系统要求 ⚠

| | |
|---|---|
| **后果** | 生成的 DOCX 排版不符合申报系统模板，企业仍需大量手工调整 |
| **应对** | 阶段一先用官方模板反向定 Markdown 结构；DOCX 输出在第 2 周做，预留调整时间 |
