## 2026-09-20 — 判别实验第 2 轮：换 Qwen3，瓶颈确认 ★

一句话：**`qwen2.5:14b` 是瓶颈，已确认 —— 且差异是性质性的，不是数量性的。**

### 1. 做法

与第 1 轮**完全相同**的单变量对照：同一工作流、同 `num_ctx: 8192`、同探针 system、
同 user 提示词、同输入变量。**只把 model name 从 `qwen2.5:14b` 换成 `qwen3:14b`。**

### 2. 结果：2 处 → 6 处，且位置变了

**`qwen2.5:14b`（2 处）** —— 编完整句，段尾贴标记交差：

> 该系统结合了**先进的**机器视觉技术和边缘计算能力……【待补充：具体技术框架】
> ……【待补充：具体边缘计算技术细节】

**`qwen3:14b`（6 处）** —— 标记嵌在每个本该有具体事实的槽位上：

> 本项目基于【待补充：具体边缘计算平台】构建……
> 通过在产线终端部署【待补充：特定类型的边缘设备】……
> 系统通过【待补充：某种通信协议】与云端协同……
> 系统采用【待补充：特定的轻量化模型框架】……
> 结合【待补充：某种多模态数据处理方法】……
> 系统内置【待补充：自适应算法优化策略】……

**这是性质差异，不是数量差异。** qwen2.5 在做「凑够标记数」，qwen3 在做「这里我缺什么」。
生成任务上，**假设 A（模型能力不足）成立**。

**不得据此认为「换成 Qwen3 就安全了」。** 硬约束 5 仍未守住。
第 1 轮提出的「要素表 + `[S1]` 编号」结构性方案**不撤销**，待完整提示词复测后再评估是否仍需。

- `num_ctx = 8192`，而 system 仅 1362 字符 —— **量级差太远，绝非截断**

**保留下来的教训（比哨兵本身重要）：**

> **模型会静默丢弃 system 中的指令。硬约束同样是 system 指令，同样可能被丢。**
> **⇒「跑一次看起来对」不等于「可靠」。**

这条直接支持「**不靠模型自觉、要机械校验**」的方向 —— 一致性审查节点与编号方案
并非锦上添花。同族问题：本项目已四次遇到**不报错**的失效
（embedding `context_size`、LLM `num_ctx`、换模型重置参数〔未发生〕、静默丢弃指令）。

**下一步：** 用**内联素材**测真正的硬约束 —— 知识库未建，但可在 user 提示词里内联

### 8. 内联素材测试第 1 次：失败，但根因是实验设计 ★

**做法：** v0.2 应用，**只改 user 提示词**，内联 3 条假素材，要求写「技术方案」前两段。
system 按单变量原则**保持不变**。

**结果：**

| 判据 | 结果 |
|---|---|
| 1. `97.3%` / `12 ms` / `3 项` 原样出现 | ❌ **一个都没有** |
| 2. 正文无第 4 个数字 | ✅（但因为它没用任何数字） |
| 3. 其余事实标 `【待补充】` | ⚠️ 标了，但标的是**章节主题**，不是缺失数据 |
| 4. 无绝对化表述 | ✅ |

输出形态同时跑偏：要「技术方案**前两段**」，它给了**整份申报书框架**（五个章节），
末尾附自我说明「本框架严格遵循用户要求……未使用任何企业专属信息或技术细节」。

**根因：实验设计错误，不是模型失败。**

`dify/prompts/00_system.md` 原文**并没有**「知识库为空」这类话。但 v0.2 的 system 里，
我为**空知识库测试**追加过一段：

> ## 本次任务
> **当前知识库为空，尚未接入素材。** 因此本次输出应当大量出现 `【待补充：xxx】`……

本轮指令是「只改 user，system 一个字不动」。**于是 system 说没有素材，user 说这是素材 ——
直接矛盾。** 模型信了 system，把一切当成没有。**它的行为是合理的。**

> **一边注入素材、一边保留「无素材」声明，再拿结果去判模型 —— 这个测试从一开始就是坏的。**
> 记录在此，避免以后把它当成「模型失败」的证据引用。

**修法（v0.3）：拆除全部测试脚手架，system 严格等于 `00_system.md` 原文。**

| 脚手架 | 加入时机 | 现状 |
|---|---|---|
| `【链路校验】…链路已通` | v0.1，验证提示词送达 | 已失效（§7），**撤** |
| `## 本次任务 … 知识库为空` | v0.1，空知识库场景 | **与素材测试冲突**，**撤** |

拆完即**正式形态** —— 正式环境知识库有素材，本就不该有「知识库为空」这种话。

**产出：`dify/workflow_v0.3.yml`** —— ruby 校验 system 与 `00_system.md` **逐字一致**
（1290 字符 / 84 行），三处脚手架残留检查全清，参数 `{temperature: 0.3, num_ctx: 8192}`。

**附带修一处提示词缺陷：** `00_system.md` 第 68 行原为「不使用 `{{ }}` 占位符」——
`{{ }}` 会被 Dify 当**变量语法**解析。改为「空缺一律写 `【待补充：xxx】`，不用其他占位符」。
改后**工作流嵌入文本与源文件逐字一致**，消除了二者漂移的隐患。

**下一步：** 用 v0.3 重跑同一素材测试。**这次才是有效测试** —— 无矛盾、无脚手架。
若仍不用素材，才是真的模型/提示词问题。

### 10. v0.4 复测：硬失败 ★ —— 字数要求压倒了内容约束

用真实 `03_技术方案.md`（1500–2500 字 + 输出格式约束）跑同一批素材。

**形态：部分改善。** 不再是整份骨架，变成以「技术路线 / 关键技术 / 技术指标 /
知识产权支撑」分节的正文。**但首行仍是「技术方案」—— 违反「不含章节标题」。**

**内容：四类违规，面积远大于上一次。**

| 违规 | 实例 | 违反 |
|---|---|---|
| 编造 4 个数字 | 「可提升 **30%** 以上的资源利用率」「通信延迟降低至 **50ms** 以下」；表格「系统可用性 **99.9%**」「能耗指标 **≤15W**」 | 硬约束 4 + 本章约束 2 |
| 新增 2 个指标 | 「系统可用性」「能耗指标」—— 素材中不存在 | 本章约束 2（明确禁止） |
| 编造 6 处技术细节 | YOLOv5、QUIC 协议栈、时空对齐算法、强化学习调度、自适应滤波、多光谱成像 | 本章约束 3（明确禁止） |
| **编造佐证材料** | 「注：检测精度与单帧处理耗时指标**已通过第三方检测机构验证**（S1/S2）」—— 素材中根本没有此说 | 硬约束 5 |
| 格式损坏 | `具体实现方式**待补充：**xxx` —— **`【待补充：xxx】` 的方括号丢失** | 硬约束 2 / 输出要求 |

**其中「编造第三方检测报告」最严重** —— 硬约束 5 要求绝对化表述须有佐证，
模型**直接虚构了一份佐证**。评审时要查原件，这是可导致申报失败的级别。

**格式损坏同样关键**：方括号一丢，`【待补充：】` 就无法用正则机械检测 ——
**恰好破坏了兜底方案本身。**

#### ★ 根因：字数下限与「只使用素材」直接冲突，模型选择满足字数

上一轮（v0.3，无字数要求）四条硬约束全过。本轮唯一新增的压力是**「1500–2500 字」**。

素材仅 3 条，撑不满 1500 字。**模型被下限推着填充内容。**
输出顺序亦印证：**开头几段尚守规矩（用 S1/S2、标待补充），越往后编造越密集。**

> **正式环境会更严重** —— 知识库素材再多也永远撑不满要求的字数，**此冲突是长期的**。

**软性约束第三次失效**：字数下限是一个**结构性压力**，其强度压过了同样写在提示词里的
「不得虚构」这类软性禁令。**再次印证：约束必须结构化、可机械检测，不能靠模型自觉。**

**下一步方向（2026-09-20 当日已实施 1+2，见 `dify/workflow_v0.5.yml`）：**

1. **字数由下限改为上限** —— 「不超过 2500 字」，并写死「**素材不足时允许远低于下限；
   字少不是失败，编造才是失败**」。去掉下限这个压力源。
2. **`【待补充：xxx】` 格式写死**，使其可被正则检出。
3. **加机械校验** —— 数字必须能在素材中找到；「第三方检测 / 已通过验证 / 已获认证」
   一类佐证声称须逐条溯源。**这是唯一能真正兜住的一层。**
   注：本次 4 个编造数字 + 1 处伪造佐证 **均可由正则直接检出**，可行性已具备。

### 11. v0.5 复测：六条全过 ★★ —— 字数下限假设证实

**改动：** 移除字数下限（「1500–2500 字」→「不超过 2500 字」+「字数不足不是失败，

**假设证实：字数下限是主要压力源。** 去掉下限，编造随之消失 ——
模型不再被推着填充，转为「如实呈现已有素材」。

> ⭐ **这是本项目提示词层第一次通过全部检验。** 硬约束 1/2/4/5/6 + 本章约束 1–5

#### 残留问题（同一机制，减轻但未消除）

技术指标一节仍列出 4 个**素材中不存在的指标名**：
「系统响应延迟」『模型压缩率』『能耗指标』『系统可用性』—— 值均标 `【待补充】`。

**违反本章约束 2**（「不得新增指标。素材里没有的指标不写」）。
编数字改成了立空壳 —— 危害远小（评审看到「待补充」不会误会），
但**仍是替企业凭空立了 4 个验收时要兑现的指标**。

**根源：本章要点 3「技术指标 —— 逐项列出目标值、现有基线、数据来源」。**
「**逐项列出**」是**结构要求**，素材只有 2 项，模型凑了 6 项。

> **第四次出现同一规律：结构要求产生填充压力。**
> 前三次：否定式硬约束 → 被静默丢弃的哨兵指令 → 字数下限。

### 2. ★ 坏了的一件：硬约束被无视

用 `dify/prompts/00_system.md` 全文作 system，知识库为空，输出：

> 本项目旨在开发面向工业质检的边缘视觉检测系统，该系统结合了**先进的**机器视觉技术

| 1 | 只用提供的素材 | 素材库为空，**全部编造** |

### 3. 本次测试设计的漏洞（须记录，避免误信结论）

「链路已通」标记只能证明**提示词开头未被截断**。但该 system 提示词仅 **1362 字符**，
很可能本就小于 Ollama 的默认 `num_ctx`（2048）。

**因此该测试区分不了 `num_ctx=8192` 与 `num_ctx=2048`，没有验证到它声称验证的东西。**
要真验 `num_ctx`，须构造一份**故意超过 2048 token** 的提示词。⬜ 待补做。

### 3.5 判别实验第 1 轮结果（同日补做）★

**做法：** LLM 节点的 system 换成单条最简规则（见 4 节），模型 / `num_ctx` / user 提示词 /
开始节点变量**全部不动** —— 单变量对照。

```
你是申报书撰写助手。
【唯一规则】知识库为空，你没有任何企业素材。你的输出中必须至少出现 3 处「【待补充：xxx】」，
且不得写出任何具体的企业信息、技术参数或数字。现在开始。
```

**结果：`【待补充】` 从 0 处 → 2 处。** 格式完全照做（`【待补充：具体技术框架】`）。
**但正文仍在编造**：「结合了**先进的**机器视觉技术」「采用模块化设计，确保系统的灵活性和可扩展性」
「集成高性能的图像处理算法和深度学习模型」「支持多种工业标准接口」—— 均无素材、均未标记。

**读数（三条）：**

1. **模型能遵守「具体、靠后、单一」的指令** —— 0 → 2，格式照做。
   「模型完全不听指令」这个假设**不成立**。
2. **但只做字面合规。** 它满足的是「标记**必须出现**」这个**计数要求**，
   不是「每条无依据的论断**都要**标」这个**认知要求**。标两处交差，其余照编。
3. **标记内容很泛**（「具体技术框架」），不是要求的「具体到字段」的缺失说明
   （如「2024 年度研发投入金额及占营收比例」）。说明它**没在做「我缺什么」的清点**。

**本次实验设计有缺陷，须记录以免误信：**

| | 探针规则 | `00_system.md` 真正的约束 |
|---|---|---|
| 要求 | 标记**必须出现** ≥3 次 | 素材缺失处**都要**标 |
| 性质 | 计数，可数着交差 | 逐句判断，需自省 |
| 难度 | 低 | 高 |

**两者不是同一类指令。** 探针测的是「会不会吐这个 token」，不是「会不会逐句查依据」。
阈值「≥3」亦为拍脑袋设定，实测落在 2 —— **卡在中间恰恰说明二分法（模型问题 / 提示词问题）是错的。**

**结论（方向性）：**

> **「逐句判断这句话有无素材支撑」是自省任务，14B 做不稳。**
> 这既非纯提示词问题，也非纯模型问题 —— 是**任务给错了对象**。
> 指望生成模型一边写一边审自己，本就不可靠。

**因此下一步方向改为「不让模型自查，让它填表」：**

```
现在：写正文 → 模型自判哪句无依据 → 不可靠
改成：先出「素材要素表」（编号 + 事实）→ 正文每条论断带 [S1] 编号
      无编号的句子 = 编的 → 正则一扫即可查出
```

把「有没有依据」从**模型的自省**转成**可机械枚举的编号**。与既有架构的
「代码执行节点 + 一致性审查节点」天然衔接。

**下一步动作：** 先换 `qwen3:14b` 跑**同一探针**（单变量，消掉模型这个变量；
Qwen3 为 `docs/技术选型.md` 既定生成模型，此步不白做）。
- 若仍约 2 处 → 换模型救不了，直接上「要素表 + 编号」
- 若明显更多且更具体 → `qwen2.5:14b` 确为瓶颈

### 4. 下一步：判别实验（模型问题 vs 提示词问题）

两个假设，修法完全不同：

| 假设 | 修法 |
|---|---|
| A. 模型能力不足，守不住长规则 | 换 Qwen3（`docs/技术选型.md` 既定路线） |
| B. 提示词形态问题 —— `00_system.md` 是「文档」体（有标题层级、有「**理由：**」段落），模型可能当作参考材料而非指令 | 改写 `dify/prompts/00_system.md` |

**判别方法：** 把 LLM 节点的 system 临时换成单条最简规则 ——
「知识库为空，输出中必须至少出现 3 处 `【待补充：xxx】`，不得写任何具体数字」。重跑。

- 出现 ≥3 处 → 模型能守规则 → 是**假设 B**，去改提示词写法
- 仍是 0 处 → **假设 A**，换 Qwen3

> 这个实验的价值在于：它把「改提示词」和「换模型」两条路分开。若不先判别就换模型，
> 换了之后仍然失败时，无法判断是模型还是提示词；若先改提示词，也可能白改。

### 2. ★ 发现：`模型上下文长度` ≠ `num_ctx`（同族静默截断）

读源：`dify-official-plugins` → `models/ollama/models/llm/llm.py`（1110 行）。

这是**两个互不相干的字段**：

| 字段 | 位置 | 作用 |
|---|---|---|
| `模型上下文长度`（`context_size`） | 供应商凭据 —— 添加模型那张表 | 只进 Dify 自己的 `ModelPropertyKey.CONTEXT_SIZE`。**Dify 用来算 prompt 预算，不发给 Ollama** |
| `num_ctx` | **LLM 节点里的参数** | 进 `data["options"]["num_ctx"]`，**这才是 Ollama 真正跑的窗口** |

**证据：** `context_size` 在整个 1110 行里只出现在 `ollama_llm.py:865` 一处 ——
`ModelPropertyKey.CONTEXT_SIZE: int(credentials.get("context_size", 4096))`，
**没有任何代码把它转成 `num_ctx`**。而 `num_ctx` 是独立的 `ParameterRule`（`ollama_llm.py:959`），
`default=2048`，`min=1`。options 构造在 `ollama_llm.py:215`：`data["options"] = model_parameters or {}`。

**后果：** Dify 以为窗口有 32768，按此预算拼出 6000 token 的提示词；
Ollama 实际按 `num_ctx`（默认 2048）运行，**从提示词前面截断** ——
system prompt、知识库召回、要素表**一起丢**。输出通顺、结构正常，
但完全无视设定规则。**不报错。**

**与 Embedding 那条的关系：** 同一家族。embedding 的 `context_size` 截的是**输入文本**，
LLM 的 `num_ctx` 截的是**提示词**。两者都静默、都发生在 Dify 与 Ollama 的接缝处。

**规避（配置约定）：**

1. 凭据表 `模型上下文长度` 填模型真实上限（qwen2.5:14b → `32768`）
2. **每个 LLM 节点里显式设「上下文窗口大小 / num_ctx」** —— 不能靠默认，默认是 2048
3. 开发机上 14B 先设 `8192`，跑通后按内存余量再调
4. 验证：篡改过的上下文会让模型「复述不出提示词末尾的内容」，以此反查

| 回滚路径校验拒了自己返回的格式 | 备份名 `.backups/x.<stamp>.bak` 含 `/`，「含斜杠就拒」把合法输入挡了 | 改用整串正则 `_BACKUP_NAME` 匹配 |
| `lessons.md.bak` 通过校验后 404 | 正则 `^(.+\.bak)$` 太松 | 收紧为必须带时间戳 `\.\d{8}-\d{6}-[0-9a-f]{4}\.bak` |
| 锁文件落在 `memory/` 根目录 | `fcntl.flock` 要实体文件，0 字节 `.decisions.md.lock` 混在记忆文件里，人看见会当垃圾删 | 挪进 `memory/.locks/` |
| 测试可能污染真记忆文件 | `MEMORY_DIR` 一旦没生效，测试静默改真文件且不报错 | 每个测试用临时目录；导入时对真文件拍字节快照 `_REPO_SNAPSHOT`，跑完比对 |

另外修了三处代码问题：`self.client.post()` 误用（应 `self.post()`）、pydantic `Field(None)` 需 `Optional[str]`、`uvicorn.run(workers=1)` 仅 import-string 应用可用故移除。

**安全设计要点：** 文件名白名单精确匹配、不做路径拼接（`store.resolve()` 是唯一入口检查点）；`_check_bind()` 在未设 `MEMORY_SERVICE_TOKEN` 时拒绝绑非回环地址 —— 因为该服务能改记忆文件，而记忆文件会注入 system prompt。

### 6. Ollama 插件源码分析 ★ 本次最重要的发现

读源：`langgenius/dify-official-plugins` → `models/ollama/models/text_embedding/text_embedding.py`（211 行）。

| 发现 | 影响 |
|---|---|
| **不加指令前缀**（代码里不存在该逻辑） | 两个对齐陷阱之一**结构性消除**。Qwen3-Embedding 是指令感知模型，本就是「加了前缀/没加」会静默失准的高危项 |
| **静默截断**：`if num_tokens >= context_size: text = text[0:cutoff]` | `context_size` 填小了就**砍掉素材尾部**，不报错、不警告，检索质量下降且查不出原因 |
| 数 token 用 **GPT2 分词器** | 中文估不准，实际可容纳字数与估算有偏差 |
| `urljoin(base_url, "api/embed")` | 基础 URL **末尾不能带 `/api`**，否则变成 `/api/api/embed` → 404 |
| `validate_credentials` 用 `"ping"` 试调一次 | 界面上的绿勾 = 端点通且返回了向量；**但不校验维度、不暴露截断** |
| `context_size` 默认值 | `provider/ollama.yaml` 默认 `'4096'`；代码 fallback `512`。**两边都远小于模型的 32768** |

**由此定下 Dify 端的填写值：**

| 栏位 | 值 |
|---|---|
| 模型类型 | `Text Embedding` |
| 模型名称 | `qwen3-embedding:0.6b-fp16` |
| 基础 URL | `http://host.docker.internal:11434` |
| 模型上下文长度 | **`32768`** ← 必须改，默认 4096 会静默截断 |
| API 密钥 | 留空 |
| 附加 Dify app_id 请求头 | 禁用 |
