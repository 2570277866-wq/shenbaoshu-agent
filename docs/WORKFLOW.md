## 一、提示词全景

**提示词全文在 `dify/prompts/`，一节点一文件。** 本节只给索引与关键约束。

> ⚠️ 提示词全文**不在此处重复** —— 见 `memory/decisions.md`「一个事实只有一个落点」。要在此内联全文，说一声即可。

| 文件 | 对应节点 | 输入变量 | 输出 | 字数 |
|---|---|---|---|---|
| `00_system.md` | 全部 LLM 节点共用 | — | 约束条款 | — |
| `01_要素抽取.md` | 代码节点 ①（规则）+ LLM 兜底 | `kb_material_*`, `in_team_size` | `gen_elements` | — |
| `02_项目背景.md` | 迭代 · 章节 1 | `gen_elements`, `kb_material`, `kb_style`, `in_project_highlights` | `gen_section_background` | 800–1200 |
| `03_技术方案.md` | 迭代 · 章节 2 | 同上 + `kb_material_tech`, `kb_material_ip` | `gen_section_tech` | 1500–2500 |
| `04_实施计划.md` | 迭代 · 章节 3 | `gen_elements`, `in_team_size` | `gen_section_schedule` | 800–1200 |
| `05_团队基础.md` | 迭代 · 章节 4 | `gen_elements`, `in_project_leader` | `gen_section_team` | 600–1000 |

| `09_一致性审查.md` | 审查 · LLM 语义部分 | `gen_document`, `kb_style` | `chk_llm_report` | — |

### 各章节的核心约束（速查）

| 章节 | 最易出错的地方 | 约束要点 |
|---|---|---|
| 项目背景 | 引用来路不明的行业数据 | 政策名称/文号必须有素材；行业数字没有就标 `【待补充】` |
| 技术方案 ★ | 指标被改写、专利号杜撰 | 指标值与 `core_metrics` 完全一致；专利号只能来自 `ip_list` |
| 实施计划 | 人数与周期前后矛盾 | 与 `gen_elements.team_size` / `duration_months` 一致 |
| 团队基础 ★ | 虚构学历、职称、获奖 | 素材没写的个人信息一律不写 |
| 预期成果 ★ | 虚报经济效益 | 每项指标要有验证方式；不确定的产值不写 |
| 经费预算 ★ | 推算分项金额 | 分项之和与总额不符时**原样呈现并标注**，不倒推 |
| 风险应对 | 套路化套话 | 风险具体到环节；不写自我否定表述 |

★ = 高风险章节，人工审核重点。

## 二、变量传递路径

```
in_* (10个)
   │

   │
   ├──────────────► 知识检索 ──┬──► kb_template

   │                          ├──► kb_material_finance┤

                                              │

                                        gen_elements ★
                                              │
                    ┌─────────────────────────┼─────────────────────────┐
                    ▼                         ▼                         ▼
              [迭代节点]                [各章节 LLM]              [代码节点②]
              决定生成哪些章节           共享同一份要素表           模板替换
                    │                         │                         │
                    └──────────┬──────────────┘                         │
                               ▼                                        │
                        gen_section_*                                   │
                               └────────────────────────────────────────┘
                                              │
                                              ▼

                                              │
                    ┌─────────────────────────┴──────────────┐
                    ▼                                        ▼
          [代码节点③ 确定性检查]                    [LLM 语义审查]
          数字回溯/一致/占位符/字数                  缺口密度/风格串事实
                    │                                        │
                    └──────────────► chk_report ◄────────────┘
                                        │

```

### 传递规则表

| 从 | 到 | 传什么 | 关键性 |
|---|---|---|---|
| 开始 | 文档提取器 | `reference_files` | 可选 |
| 文档提取器 | 知识检索 | `doc_guide`（评审要点） | 提高检索精度 |
| 知识检索 | 代码节点① | 三个素材库的召回结果 | **必需** |
| 知识检索 | 各章节 LLM | `kb_style` | 提供表达风格 |
| 代码节点① | **全部章节 LLM** | `gen_elements` | ★ 一致性根基 |
| 代码节点① | 代码节点③ | `gen_elements` | 校验基准 |
| 各章节 LLM | 代码节点② | `gen_section_*` | |
| 代码节点② | 代码节点③ + LLM 审查 | `gen_document` | |
| 代码节点③ | 条件分支 | `chk_report` | 决定回退 |

### 三条传递铁律

1. **`gen_elements` 必须先于迭代节点产生。** 顺序颠倒 = 各章节各自为政 = 章节间数字打架。
2. **`kb_material` 只进素材渠道。** 不把 `kb_style` 混进素材变量，否则风格库的事实内容会被当作事实引用。
3. **章节 LLM 之间不互相传递。** 章节 A 的输出不进章节 B 的输入 —— 一旦串联，错误会沿链放大，且无法并行。

## 三、迭代节点的分块策略

### 3.1 分什么块

迭代节点处理的是**章节级分块**，不是文本级分块。

| | 做法 | 理由 |
|---|---|---|
| ✅ 章节边界分块 | 一次迭代生成一个完整章节 | 章节内部语义连贯，上下文完整 |
| ❌ 固定字数硬切 | 每 2000 字一块 | 会切断论证，产生"上半句说 A，下半句说 B"的碎片 |

**章节数由模板决定**，不写死。模板有几个 `{{gen_section_*}}`，迭代就转几次。

### 3.2 迭代单元定义

```json
{
  "sections": [
    {"key": "background", "title": "项目背景与意义", "prompt": "02_项目背景.md", "words": [800, 1200]},
    {"key": "tech",       "title": "技术方案",       "prompt": "03_技术方案.md", "words": [1500, 2500]},
    {"key": "schedule",   "title": "实施计划",       "prompt": "04_实施计划.md", "words": [800, 1200]},
    {"key": "team",       "title": "团队与基础条件", "prompt": "05_团队基础.md", "words": [600, 1000]},
    {"key": "outcome",    "title": "预期成果",       "prompt": "06_预期成果.md", "words": [800, 1200]},
    {"key": "budget",     "title": "经费预算",       "prompt": "07_经费预算.md", "words": [500, 800]},
    {"key": "risk",       "title": "风险与应对",     "prompt": "08_风险应对.md", "words": [500, 800]}
  ]
}
```

**章节清单本身来自模板**（代码节点② 解析 `templates/申报书模板.md` 得出），不由 LLM 自由决定 —— LLM 决定章节会导致每次生成的章节数不一致。

### 3.3 上下文预算

单次迭代要装进上下文的内容：

```
系统提示词 (00_system.md)
+ 本章节提示词
+ gen_elements          ← 全局要素表，每章都要，不可省
+ 本章节相关的 kb_material  ← 只给本章相关的，不给全部
+ kb_style 相关段落      ← top-2 即可
+ in_* 相关变量
```

**关键取舍：`gen_elements` 每章都全量注入。** 它只有几百 token，但省掉它 = 章节间数字不一致。

**素材只给本章相关的。** 写"经费预算"时不需要给专利清单。按章节做二次检索，不要一次把全部素材塞进去。

### 3.4 串行 vs 并行

| 模式 | 说明 | 采用 |
|---|---|---|
| 串行 | 逐章节依次生成 | ✅ 阶段一默认 |
| 并行 | 多章节同时生成 | ❌ 显存不足，Ollama 串行 |

单机单卡下，并行只会导致排队与 OOM。**阶段一接受串行，总耗时 20–40 分钟可接受。**

### 3.5 长章节的二次分块

单章节超过模型上下文时（如技术方案 2500 字 + 素材），按**段落边界**二次分块：

1. 按三级标题切分为子节
2. 子节间传递已生成内容摘要（≤ 200 字），保持衔接
3. **表格、代码块不跨块切分**

这是例外路径，正常章节不需要。

## 四、一致性审查的输入组装方式

### 4.1 组装顺序：先代码，后 LLM

```
gen_document ──┬──► 代码节点③ 确定性检查 ──► chk_code_report ──┐
               │        (数字/占位符/字数)                        │
               │                                                 ▼
               └──► LLM 语义审查 ◄──────── 组装 ──────────► chk_report
                        (缺口密度/风格串事实)
```

**先代码的原因：**

1. 数字问题用正则与比对可确定判定，不需要 LLM，省一次推理
2. 代码检查发现严重问题可**短路回退**，不必再调 LLM
3. 代码判定不会误报，LLM 判定会

### 4.2 代码节点③ 的输入组装

| 输入 | 用途 |
|---|---|
| `gen_document` | 被检查对象 |
| `gen_elements` | 数字一致性基准 |
| `kb_material_*` | 数字回溯比对源 |
| 原始模板 | 占位符清单（比对是否全替换） |

**执行七项中的 1/2/3/4/6 项**：全局数字一致、数字可回溯、无杜撰资质、占位符无残留、章节字数达标。

### 4.3 LLM 审查的输入组装

| 输入 | 用途 |
|---|---|
| `gen_document` | 被检查对象 |
| `kb_style` | **比对是否串入范文事实** |
| `gen_elements` | 辅助判定 |
| `chk_code_report` | 已有结论，避免重复报同一问题 |

**执行 5/7 两项**：空缺密度统计、风格未串事实。

### 4.4 两份报告的合并

```json
{
  "pass": false,
  "code_issues": [ ... ],
  "llm_issues": [ ... ],
  "issues": [ ... ],
  "stats": {"tbd_count": 3, "word_count": {...}, "retry_count": 1}
}
```

**合并规则：**

| 情况 | 处理 |
|---|---|
| 任一 `critical` | 直接回退，阈值不讨论 |
| 仅 `high`/`medium` | 回退问题章节，上限 2 次 |
| 仅 `low` | 不回退，记入报告交人工 |
| 两份报告报同一问题 | 按 `critical` 去重合并 |

**只回退问题章节，不整篇重生成。** 整篇重生成会引入新问题，且耗时翻倍。

## 五、异常处理

### 5.1 异常分类与处理

| # | 异常 | 检测点 | 判定 | 处理 | 用户看到 |
|---|---|---|---|---|---|
| E1 | **材料不足** | 代码节点① · `missing` 非空 | 缺关键字段（负责人/预算/人数） | 不阻断，继续生成 | 对应位置 `【待补充：xxx】` + 报告顶部提示清单 |
| E2 | **材料不足（重度）** | 代码节点① · `missing` > 阈值 | 缺 5 项以上关键字段 | **阻断**，不出稿 | 提示"素材不足，需补充以下材料：…" |
| E3 | **检索为空** | 知识检索 · 素材渠道 top-k 全空 | 三库均无命中 | **阻断** | "知识库未检索到该企业素材，请确认素材已入库" |
| E4 | **检索为空（部分）** | 知识检索 · 单库为空 | 某类素材库无命中 | 不阻断 | 该维度标注 `【待补充】`，记入 `missing` |
| E5 | **生成超时** | 迭代节点 · 单章节耗时 | > 单章节超时阈值 | 重试 1 次 | 仍失败则跳过该章节，标注 `【本章生成失败，需人工撰写】` |
| E6 | **生成超时（整体）** | 工作流总耗时 | > 60 分钟 | 不中止，但告警 | 继续等待，同时推送告警 |
| E7 | **模型服务不可用** | 各 LLM 节点 | 连接失败 | **阻断** | "模型服务异常，请联系管理员" |
| E8 | **显存不足** | 各 LLM 节点 | OOM 异常 | 降级：减小 top-k 与上下文，重试 1 次 | 成功则继续（质量略降），失败则阻断 |
| E9 | **审查不通过** | 条件分支 | `pass: false` | 回退问题章节，上限 2 次 | 超限则出稿 + 问题清单，标"待人工核校" |
| E10 | **DOCX 转换失败** | HTTP 节点 | 非 2xx | 降级：输出 Markdown | 提供 Markdown 下载 + 提示转换失败 |
| E11 | **模板占位符残留** | 代码节点② | 替换后仍有 `{{` | 不阻断 | 报告标出残留位置 |

### 5.2 阻断 vs 降级原则

| 类型 | 判断标准 | 例子 |
|---|---|---|
| **阻断** | 继续生成会产生**看似合理但错误**的结果 | E2 素材严重不足、E3 检索全空、E7 模型不可用 |
| **降级** | 继续生成的结果**明显不完整**，人看得出来 | E5 单章节失败、E8 显存降级、E10 DOCX 转换失败 |

**核心判断：宁可产出明显残缺的稿子，不可产出看起来完整但内容错误的稿子。** 前者人工一眼看出，后者可能直接提交出去。这是 R1 风险的执行细则。

### 5.3 超时阈值

| 项 | 阈值 | 依据 |
|---|---|---|
| 单章节生成 | 8 分钟 | 待实测校准 |
| 单章节重试 | 1 次 | |
| 整体工作流 | 60 分钟 | 超时告警，不中止 |
| 知识检索 | 30 秒 | |
| DOCX 转换 | 60 秒 | |

> 全部待实测校准。第 1 周 D2 完成基线测量后回填。

### 5.4 异常记录

每次异常写入运行日志，含：异常类型、发生节点、输入摘要、处理动作、最终结果。

**异常统计是知识库缺口的信号源：** E1/E4 高频出现的素材类型 → 通知 B 补充。这条与 `memory/lessons.md` 的每周复盘闭环对接。

## 六、版本管理

导出文件名：`dify/workflow_v<主>.<次>.yml`

改动流程：

1. Dify 界面修改
2. 提示词改动同步 `dify/prompts/`
3. 导出 `workflow_vX.Y.yml`（次版本 +1）
4. `memory/decisions.md` 记录改了什么、为什么
5. 更新本文档与 `docs/ARCHITECTURE.md`（若涉及编排）
6. 更新 `CLAUDE.md`「当前任务」
